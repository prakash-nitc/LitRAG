# Architecture

LitRAG is ~1k lines of plain Python. Every stage reads and writes a file you can
open, so any intermediate result can be inspected or swapped out.

## Data flow

```
scripts/download_corpus.py   arXiv  ->  corpus/<Paper>.pdf
litrag/ingest.py             PDF    ->  index/chunks.jsonl          {paper, idx, text, n_words}
litrag/embed_index.py        chunks ->  index/dense_<model>.npz     vectors (N, d) + metadata
litrag/search.py             query  ->  top-k Hit(score, paper, idx, text)
litrag/generate.py           hits   ->  answer text with [paper:idx] citations
litrag/eval.py               QA set ->  recall@k / MRR / answer-quality metrics
app.py                       Gradio front end over search + generate
```

## Modules

| module | responsibility | notes |
|---|---|---|
| `ingest.py` | PDF text extraction, cleanup, word-window chunking | the only place chunk size/overlap are set |
| `embed_index.py` | embedding model registry + index build | query/passage instruction prefixes live next to each model name |
| `retrieve.py` | `DenseRetriever`, `Hit` | exact search: one matmul over normalized vectors |
| `hybrid.py` | `BM25Retriever`, `rrf_fuse`, `HybridRetriever` | fusion by rank, not score |
| `rerank.py` | cross-encoder second stage | reorders the first stage's top-20 candidates |
| `search.py` | `Searcher`: one entry point for every config | `mode` in {dense, bm25, hybrid} x `rerank` on/off |
| `generate.py` | prompt, Groq HTTP call, retry/backoff | no SDK; provider = one URL |
| `eval.py` | retrieval and generation metrics | see [EVALUATION.md](EVALUATION.md) |

## Design decisions

**Word windows, not sentences.** Chunks are fixed-size word windows with ~18%
overlap. Uniform sizes make the chunk-size ablation a fair comparison; sentence
splitting on PDF-extracted text is unreliable anyway (equations, captions,
two-column layouts).

**Strip the bibliography.** Everything after a `References` heading in the back
half of the paper is dropped. Reference lists contain every keyword in the field
and answer nothing, so they are pure retrieval noise. The back-half guard stops a
stray early "References" line from truncating the paper.

**Model prefixes are part of the model.** E5 expects `query:` / `passage:`
prefixes and BGE expects an instruction on queries. Leaving them out silently
lowers recall, so `MODELS` stores them with the model name and `Embedder`
always applies them.

**Exact search, no vector database.** At ~500 chunks x 384 dims, a full
`vectors @ q` is sub-millisecond. An ANN index would add a dependency and an
approximation error for no measurable gain.

**Fuse by rank.** Cosine similarities lie in [-1, 1] and BM25 scores have no
upper bound, so mixing raw scores needs fragile normalization. Reciprocal Rank
Fusion (sum of `1 / (60 + rank)` across systems) needs no normalization.

**Two-stage reranking.** The bi-encoder embeds query and passage separately,
which is fast. The cross-encoder reads them together, which is more accurate
but slower. The first stage retrieves 20 candidates and the cross-encoder
reorders them. The ablation shows this is not always a win; see the README.

**Lazy model loading.** `Embedder` and `Reranker` load weights on first use.
Importing the package is cheap, BM25-only configs never touch torch, and the
unit tests run without downloading anything.

**Grounded generation with explicit refusal.** The system prompt allows only
the provided chunks, requires a `[paper:idx]` citation after each claim, and
tells the model to say so when the context lacks the answer. `temperature=0`.
The free tier allows ~6k tokens/min, so `call_llm` backs off on 429/5xx and
honors `retry-after`.

**Degrade, don't crash.** Without `GROQ_API_KEY`, the demo shows the retrieved
evidence instead of an answer.

## Shipped artifacts

`index/chunks.jsonl` and `index/dense_bge-small-en-v1.5.npz` (~1.5 MB) are
committed so the demo starts instantly on HF Spaces. `tests/test_shipped_data.py`
checks that the two stay row-aligned. Everything else under `index/` and
`results/` is regenerated by the scripts.

## Scaling limits

This design is sized for a few thousand chunks. Past ~100k chunks, the changes
would be: an ANN index (FAISS / HNSW) in place of the full matmul, a persisted
BM25 index in place of the in-memory build at startup, and batched/cached query
embedding in the demo.
